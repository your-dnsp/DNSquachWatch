# microSD responsiveness follow-up — v1.5.7

Hardware observation: without microSD the main screen held approximately 20–21 fps, with about 2 ms in the pre-drawing profiler lap. With the card, that lap previously reached approximately 80 ms and the user observed intermittent motion and touch stalls. This isolates a card-dependent path; it does not establish a defective card.

Automatic readable-history refresh formerly appended a record and performed its pending-record and checkpoint transactions together before drawing. Preparation now separates pending-ID writing from verification, each record leaf is appended separately, and checkpoint write, verification and completion each advance in their own pass. Final summary and schema markers also advance separately. Raw log chunk copying separates its append from the copy-cursor transaction.

Checkpoint writes alternate between two CRC-checked files, preserving the last validated generation while the other slot is written. Existing legacy checkpoint files remain readable. The last pending record ID is retained after commit and overwritten for the next record, avoiding delete/recreate work while preserving duplicate-safe recovery. Journal formats, bounded duplicate scanning and recovery from valid generations remain. No worker task, heap container, larger queue or additional card handle was added. Automatic refresh runs after touch and display service and pauses during active touch, the following 250 ms, and detection/rule popups. It remains enabled by default. Automatic steps start at least 250 ms apart, leaving several normal animation frames between storage steps. Manual refresh and backup keep their existing processing pace; raw event logging is unchanged. Backup uses the same staged history preparation and retains its progress and interruption protections.

Validation includes a dense 1,800-record ring, at most one durable card write per history-processing pass after initialization, interruption at successive journal passes, retry without duplicates, write failure recovery, bounded reads and two-handle limits. UI tests and both 80 MHz display builds are checked separately.

Limits: filesystem access remains synchronous. A physical card may still stall an individual operation. Collection initialization and opening/indexing a new source file can still perform several metadata operations; ordinary raw event logging also uses the card synchronously. The main-screen drawing cost remains roughly 45–50 ms in the supplied no-card capture. No claim of 60 fps or complete hardware resolution is made. Serial output reports automatic history calls taking at least 50 ms as `[storage] history ... ms step ... slowest ... ... ms`, rate-limited to one report per five seconds. The step is captured before execution; individual file opens, reads, writes, flushes, closes, seeks, size/exists checks and directory operations are timed without printing inside the storage code. Flash-record reads and duplicate scans are identified separately. Only the slowest operation per step is retained, with unsigned elapsed time and no heap allocation. Schema-marker presence is cached for each refresh instead of checked for every committed record. That work is now outside the pre-drawing profiler lap, so that lap alone must not be used to claim a speedup.

Retest with the existing card: observe the main screen for several minutes, including after the first automatic refresh begins; dismiss a simulated detection; then complete a backup and Safe Shutdown. Capture serial at 115200 if pauses persist. Existing `/DNSP Content/v1.5/` content is unchanged. Hardware responsiveness requires confirmation on the physical card.
